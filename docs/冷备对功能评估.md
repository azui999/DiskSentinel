# 冷备对与文件校验功能 · 可行性评估

> 2026-11-12 · 基于本机实测数据（870 EVO SATA SSD 开发机），
> 全部测试限定在 `测试文件夹/` 内完成，未全盘扫描开发盘。

## 一、结论

**可行，且当前架构（PySide6 + 文件存储）不需要推翻，纯增量开发。**

但有一个必须先想清楚的架构判断：这个功能要拆成**两条通道**——

| 通道 | 做什么 | 耗时（4TB 盘） | 能发现什么 |
|---|---|---|---|
| **快通道：结构比对** | 只比文件名、大小、修改时间，不读内容 | 秒级~分钟级 | 缺文件、多文件、大小不同、漏同步 |
| **慢通道：内容校验** | 逐文件读内容算 SHA-256 | **6~8 小时/盘** | 静默损坏（你照片那种） |

你的核心动机（照片下半部分变纯色）属于**静默损坏**：SMART 正常、文件大小不变、
修改时间不变、文件系统无错误日志——**只有读内容才能发现**。所以慢通道不可省，
但它受物理极限约束（详见第四节），快通道的价值是把"明显不同步"先秒级筛出来，
让你只对"结构一致"的盘对放心跑昂贵的全量校验。

## 二、你的需求本质

还原一下场景：两块 4TB 盘互为冷备份，B 盘某文件夹十几张照片损坏
（下半部分纯色 = 文件**后半段字节翻转**），A 盘同文件夹完好。

这在冷备场景里是典型的 **bit rot（位衰减）**：消费级 HDD 的不可恢复读错率
约 10⁻¹⁴/bit，一块写满的 4TB 盘（3.2×10¹³ bit）**每次全盘读取期望出现 0~3 个
错误位**。盘越老、放得越久（不通电也会衰减，尤其 SMR 盘），概率越高。
所以"定期把冷备盘读一遍"本身就是健康动作，校验只是顺便。

由此推出本功能的判定逻辑（这是设计核心）：

```
A.hash == B.hash        → 两块同时坏成一样的概率≈0，判"两边都好"
A.hash != B.hash       → 至少一块坏，但无法判断哪块坏 → 需要"第三票"裁决
A.hash == 历史基线      → A 没变（好）
A.hash != 历史基线     → A 在两次检测之间发生了损坏/修改
```

**"第三票"就是历史基线**——这是本工具和一次性比对工具（WinMerge、FreeFileSync）
的本质区别：首次全量校验时把每块盘的哈希存档，之后每盘单独复检即可检测
"这块盘自己有没有退化"，不依赖另一块盘同时在线。这正好复用现有
"按序列号存历史快照"的思路。

## 三、数据模型（回答"文件夹要不要记录"）

**不需要单独记录文件夹。** 文件清单里每行天然带完整路径，目录树是派生信息，
任何时候都能从清单即时重建（按 `/` 分组就是目录树）。WizTree 也只存文件行，
不存目录行。想看目录级汇总时现算，500 万文件也就 1 秒的事。

每块盘每轮校验记录这些：

```
相对路径（相对盘根，正斜杠，统一小写规范化） | 大小 | mtime | SHA-256
```

盘对关系存 `data/pairs.json`：

```json
{
  "pairs": [
    {
      "name": "照片冷备对",
      "members": ["序列号A", "序列号B"],
      "root": "/",              // 校验范围：整盘，也可以是某个子目录
      "created": "2026-11-12"
    }
  ]
}
```

存储位置延续现有风格：`data/fileindex/<序列号>/`，每轮一份清单 + 一份哈希基线。

## 四、性能实测与 4TB 推算（本机数据）

| 项目 | 实测值 | 说明 |
|---|---|---|
| SHA-256 纯计算吞吐 | **2.6 GB/s** | CPU SHA-NI 硬件加速，本机（内存测试） |
| 目录遍历（SSD） | **2 万文件/秒** | os.scandir，只读元数据 |
| 读盘+SHA-256 综合 | **260 MB/s** | 真实混合文件（2~80MB），单线程 |

**关键事实：哈希计算不是瓶颈，磁盘读取才是。**
2.6 GB/s 的计算速度远超任何硬盘的读取速度，所以换更快的算法（BLAKE2b 3.2GB/s、
xxHash 更快）**没有任何意义**——瓶颈在盘。也因此 SHA-256 没有性能代价，直接用。

4TB 机械盘推算（顺序读 150~190 MB/s）：

- 全量校验一块盘：**6~8 小时**（百万级小文件会再慢些，多线程可挽回大部分）
- 两块盘全量：约 13~16 小时 → **分两次挂夜跑**，一次一块
- 之后每轮**增量**（大小和 mtime 没变的文件直接跳过）：分钟级
- 结构比对：**1~3 分钟/盘**（遍历 + 比对，不读内容）

这是物理极限，**任何校验工具都一样**。这点必须有预期：
WizTree 之所有秒扫全盘，是因为它**根本不读文件内容**——
它帮不了你发现照片损坏，这正是你要做这个工具的原因。

## 五、工具与加速手段盘点

| 工具/技术 | 对本功能的价值 | 建议 |
|---|---|---|
| **WizTree** | 秒级全盘清单（MFT 直读）。但只有元数据，**发现不了静默损坏** | 继续拿它找大文件没问题；**不引入**本工具（避免外部依赖，且它解决不了核心需求） |
| **robocopy /L /E**（Windows 自带） | 只列不拷的结构差异比对，逻辑与本工具快通道完全同款 | V1 开发时拿它当"参考答案"：同一对文件夹，本工具结果应与 `robocopy /L` 一致 |
| **Everything**（es.exe） | 秒级文件名索引，同样只有元数据 | 不引入 |
| **os.scandir** | Python 标准库遍历，实测 2 万文件/秒（SSD） | **V1 采用**，简单可靠、无权限依赖 |
| **hashlib + SHA-NI** | 2.6 GB/s，瓶颈让位于磁盘 | **采用** |
| **多线程读**（concurrent.futures） | 4~8 线程并发 hash 不同文件，HDD 上提升 20%~50%（小文件多时更明显） | V1 就做，成本很低 |
| **MFT/USN 直读**（ctypes DeviceIoControl） | WizTree 同款技术，清单从分钟级降到秒级；需管理员 + 仅 NTFS | **V2 可选**。冷备盘不常扫，scandir 的几分钟完全可接受，不急 |
| **blake2b / xxHash** | 更快的哈希 | 不用，磁盘瓶颈下无收益 |

## 六、存储方案（无数据库约束下）

规模估算：4TB 冷备盘 ≈ 50~300 万文件。每行清单（路径+大小+mtime+hash）
约 120~180 字节文本 → **单轮索引 60~500 MB/盘**。

方案：**清单与基线分开存**。

```
data/fileindex/<序列号>/
  manifest/20261112T140000.tsv    # 全量清单（含 hash 列，首轮后追加增量行）
  baseline.tsv                    # 当前生效的 hash 基线（排序后紧凑格式）
```

- **TSV 而非 CSV**：路径里逗号常见、制表符罕见，不用转义；Excel 仍能直接打开。
- **按路径排序存储**：两份索引的比对用"排序流式归并"，双指针各走一遍，
  内存 O(1)——500 万文件也只占几 MB 内存。这是不引入数据库还能扛住规模的关键。
- 比对报告写 `data/fileindex/reports/`，差异明细独立成文件，不塞索引里。

**一个需要你拍板的保留意见**：SQLite 其实是"单文件、无服务、随文件夹拷走"的东西，
和"不用数据库"的初衷（不想要服务器/二进制黑盒）并不冲突，500 万行规模下比文本
省 3~5 倍空间、查询快一个量级。但目前规模（两块 4TB、百万级）纯文本完全够用，
**V1 先用文本，不纠结**；哪天索引大到影响体验再迁移，格式转换脚本半小时的事。

## 七、坑清单（开发时逐条处理）

1. **权限拒绝目录**：`System Volume Information`、`$RECYCLE.BIN`——默认排除，
   其他拒绝项记录到报告，不静默吞掉。
2. **断点续跑**：6~8 小时的任务必须有暂停/恢复，中断后从"已完成文件列表"
   断点继续，否则一次手滑=白跑一晚。实现：进度文件记录已 hash 的路径数。
3. **大小写与路径规范化**：NTFS 大小写不敏感，比对 key 统一 lowercase；
   分隔符统一 `/`；拒绝 `\\?\` 前缀进存储。
4. **mtime 容差**：NTFS 精度 100ns，直接相等判断即可；若盘是 FAT32（2 秒精度）
   需 2 秒容差。默认假设 NTFS。
5. **hash 时文件被占用/盘掉线**：单文件失败不中断整体，记入报告"无法读取"。
6. **增量判定的漏洞**："size+mtime 没变就跳过"是假设内容没变——静默损坏
   恰恰不改这两个字段，所以**增量校验有漏检风险**。对策：增量只用于"最近同步过"
   的快速复核；**每半年（可配置）强制全量复检**。文档里必须明示这个权衡。
7. **USB 转 SATA**：冷备盘很可能走 USB 盒，hash 时掉线概率不低——断点续跑
   + 自动重试一次 + 失败清单。

P2/P3 才是"哪张照片坏了、哪块盘在退化"。

### P3 落地记录（2026-11-12）

- **单盘自检**（`app/watch.py`）：一块盘与自己的历史基线比对，不需要另一块盘在线。
  首次复检建立基线，之后每次复检报六类结果：一致 / 新增 / 丢失 / 已修改 /
  **内容损坏**（元数据未变但 SHA-256 变了）/ 无法读取。
- **基线固定不滚动**：若每次把上一轮当新基线，坏文件只报一次就被吞掉；
  现在基线一旦建立固定，每次复检都会重复点名未修复的问题，
  只有用户显式【重建基线】才重置。
- **修复 P2 遗留漏洞**：原实现跨所有历史校验沿用哈希（size+mtime 未变就跳过），
  而静默损坏恰恰不改 size+mtime——第二次校验会把"没检查"伪装成"检查通过"。
  现在默认全量重读，只有 paused 中断的校验沿用（断点续跑）；
  快速增量模式改为确认框里的显式勾选项，并全程标注。
- **校验历史页签**（`app/history_tab.py`）：结构比对 / 内容校验 / 单盘复检
  统一时间线，选中即重放该次差异明细（明细不落盘、现场从清单重算）。
- **验收**（C:\测试文件夹，102 文件样本）：首检建基线 ✔；注入 3 个静默损坏
  +1 修改 +1 删除 +1 新增 → 复检精确报出 ✔；二次复检结果不变（基线固定）✔；
  暂停 77 个 → 续跑沿用 54 补算 48 ✔；历史明细重放 ✔。

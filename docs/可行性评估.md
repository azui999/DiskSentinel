# DiskSentinel 可行性评估

> 评估时间：2026-11-12
> 评估对象：`docs/设计.md` 中的硬盘健康历史监控工具
> 复核前提：**纯 Python 桌面窗口程序，不做前后端分离，不用数据库，数据落在项目文件夹内**

---

## 一、结论

**可以做，而且比原设计更简单。**

- 技术上没有硬障碍：smartctl 的 JSON 输出 + PySide6 窗口 + 文件存储，全是成熟路径。
- 原设计里的 React + SQLite 两层（第 66、136 行）可以直接砍掉，改成 PySide6 + 文件存储，
  代码量和依赖都显著下降，功能不打折。
- MVP（扫描 → 采集 → 落盘 → 列表/详情 → 单指标曲线）预计 **1~2 天**可跑通。

**但有 4 个坑必须先解决，其中第 1 个是当前最急的阻塞项：**

| # | 坑 | 影响 | 严重度 |
|---|---|---|---|
| 1 | 仓库里的 `smartmontools-7.5` 是**源码包**，没有 `smartctl.exe` | 现在完全跑不起来 | **阻塞** |
| 2 | smartctl 在 Windows 上需要**管理员权限**，且自身不会提权 | 采集必然失败或只拿到残缺数据 | 高 |
| 3 | 你现在两块盘都是 **SSD（含 NVMe）**，SMART 结构与设计文档假设的 ATA 05/C5/C6 不同 | 按原设计写会直接 KeyError | 高 |
| 4 | USB 硬盘盒的 SMART 透传不可靠，需要 `-d` 参数兜底探测 | 外置 4TB 可能读不到 | 中 |

## 二、`smartmontools-7.5` 是否满足要求？

### 2.1 关键发现：它是源码，不是可执行文件

实际检查 `C:\wame2\DiskSentinel\smartmontools-7.5\` 的内容：

```
atacmds.cpp / ataprint.cpp / os_win32.cpp / drivedb.h / configure / Makefile.in ...
```

- 155 个文件，全是 `.cpp / .h / .in`，**没有任何 `.exe` / `.msi`**；
- 带 `configure`、`Makefile.in`、`autogen.sh`，是标准的 autotools 源码发布包；
- `configure` 中 `PACKAGE_VERSION='7.5'`。

**结论：这个目录不能直接用，也不能靠 `pip` 之类装出 `smartctl.exe`。** 在 Windows 上编译它需要
MSYS2/MinGW 或 MSVC + 一堆依赖，为了一个命令行工具做这一步完全不划算。

### 2.2 需要换成官方 Windows 二进制包

下载地址（官方）：`https://www.smartmontools.org/wiki/Download`

选 **Windows 64-bit installer**（文件名形如 `smartmontools-7.5.win64-setup.exe`），装完得到：

```
C:\Program Files\smartmontools\bin\smartctl.exe
C:\Program Files\smartmontools\bin\smartd.exe
```

两种情况都行：

- 装到 `C:\Program Files\smartmontools`（推荐，路径固定，程序里做默认值 + 自动探测）；
- 或者解压版直接把 `smartctl.exe` 拷进项目 `tools/` 目录下，跟着项目走，免安装。

> 顺带说明：源码包不是没用。`smartctl.8.in`（手册）、`os_win32.cpp`（Windows 设备名与权限行为）、
> `nvmeprint.cpp`（NVMe 的 JSON 字段）都是很好的"权威参考"，读它比读博客靠谱。本评估的第 3、4 节结论就是这么来的。

### 2.3 版本 7.5 本身够不够

够。7.5 是 2025-04-30 的版本，已确认包含本工具需要的全部能力：

- `-j` / `--json`：JSON 输出（`smartctl.8.in:327`）；
- ATA/SATA 属性表、SMART 自检日志、错误日志；
- NVMe 健康日志（`nvmeprint.cpp:510` 输出 `percentage_used` 等字段）；
- Windows 设备支持 `/dev/pdN`、`/dev/sdX`；
- USB 桥接器兜底参数（`-d sat` / `usbjmicron` / `usbsunplus` 等，`smartctl.8.in:449-520`）。

**不需要 7.5 之外的任何东西。** 唯一要换的是"源码包 → 二进制包"。

## 三、从源码确认的几个技术事实（会直接影响代码写法）

### 3.1 Windows 的设备名

`os_win32.cpp:4634` → 扫描时生成 `/dev/pd%d`；`os_win32.cpp:4636` → 也支持 `/dev/sd%c`。
即同一块盘可以有 `/dev/sda` 和 `/dev/pd0` 两种叫法，二者都映射到 `\\.\PhysicalDriveN`。

**这条印证了设计文档第 293-306 行的判断**：设备名必须视为"本次会话的临时地址"，
硬盘身份一律用 `序列号 + 型号 + 容量` 做主键，否则拔插一次历史就断链。

### 3.2 权限：smartctl 不会自己提权

`os_win32/default.manifest` 里 `requestedExecutionLevel level="asInvoker"`。
说明 smartctl.exe 不会弹 UAC，**它继承调用者的权限**。

推论：非管理员运行时，`smartctl` 通常能打开设备但 `-a` 会报
`SMART support is: Unavailable` 或读不到属性表，且 **exit code 不为 0**。

对应设计决策（二选一，见第五节）：

- **A. 整个程序提权**：打包时 `--uac-admin`，启动即弹 UAC，逻辑最简单；
- **B. 降权运行 + 检测失败后提示重启**：体验好，但要写一个"检测 → 提权重启"的交互。

建议 MVP 用 A，稳定后再考虑 B。

### 3.3 退出码是位掩码，不是错误码

设计文档第 226 行的注释是对的，这里补全规则：

- bit 0 (1) 命令行解析错误 / bit 1 (2) 设备打开失败 → **真失败，中止**；
- bit 2 (4) SMART 命令失败 → 降级，仍可保存部分数据；
- bit 3 (8) 硬盘即将失效 / bit 4 (16) 曾经越过阈值 / bit 6 (64) 错误日志有记录 → **这是"结果"，不是"错误"**。

代码里必须写成 `if (rc & 0x03) → 失败`，而不是 `if rc != 0 → 失败`。
后者会把"硬盘正在报警"这种最有价值的信息当异常丢掉。

### 3.4 两种完全不同的 SMART 结构

这是原设计文档最大的遗漏。设计文档的 `smart_attributes` 表（第 143 行）只覆盖 ATA：

| 盘型 | JSON 位置 | 关键字段 |
|---|---|---|
| ATA/SATA（870 EVO、机械盘） | `ata_smart_attributes.table[]` | `id`(5/197/198/199), `name`, `value`, `worst`, `thresh`, `raw.string` |
| NVMe（970 EVO） | `nvme_smart_health_information_log` | `critical_warning`, `available_spare`, `percentage_used`, `media_errors`, `temperature`, `data_units_written` |

也就是说 **C5/C6 在 NVMe 上根本不存在**，硬套 ATA 那套分析逻辑会崩。

对策：内部统一抽象成"指标层"（normalized metrics），采集层负责把两种结构映射成同一组键，
上层 UI 和分析只认这套统一键。这个抽象只要写一次，后面加 SAS/USB 都不用改 UI。

## 四、推荐架构

```
DiskSentinel/
├─ main.py                  # 入口：QApplication + 主窗口
├─ app/
│  ├─ collector.py          # smartctl 调用：扫描 / 读取 / 重试 / 解码
│  ├─ normalizer.py         # ATA + NVMe → 统一指标层
│  ├─ store.py              # 文件存储读写（无数据库）
│  ├─ analyzer.py           # 趋势判断、异常检测、告警分级
│  └─ ui/
│     ├─ main_window.py     # 左：硬盘列表  右：详情 / 趋势 / 报告（QTabWidget）
│     ├─ disk_card.py       # 健康概况卡片
│     ├─ trend_chart.py     # pyqtgraph 曲线
│     └─ report_view.py     # 健康报告纯文本/Markdown
├─ data/                    # ← 所有数据都在这里（见第五节）
├─ tools/smartctl.exe       # 可选：绿色版直接放这
└─ docs/
```

**GUI 选型：PySide6 + pyqtgraph**

| 方案 | 评价 |
|---|---|
| **PySide6 + pyqtgraph** | **推荐**。原生桌面、单进程、无 HTTP；pyqtgraph 画曲线零配置、几十万点也不卡；LGPL，无授权顾虑 |
| PySide6 + QtCharts | 也可以，图表更"业务风"，但要写更多样板代码 |
| pywebview + HTML/JS | 能复用到你的前端经验，但要么内嵌静态页（交互受限），要么起本地 server——**就变成前后端了，违背你的前提** |
| Tkinter + matplotlib | 依赖最轻，但界面观感差、图表交互弱，做"科技感"很难 |

体积换来的开发效率是值得的：PySide6 约 100~200MB，装一次就好。

## 五、存储方案（不用数据库）

数据库在这个场景里是过度设计：数据量极小（一块盘一年按每天 1 次 = 365 条），
查询永远只有"某块盘的按时间序列"，SQL 的价值发挥不出来，反而多一个二进制文件不好备份、不好人眼检查。

建议这样落盘：

```
data/
├─ disks.json                        # 硬盘档案索引
├─ snapshots/
│  └─ <serial>/                      # 一块盘一个目录，目录名即身份
│     ├─ attributes.csv              # 追加写：时间,通电小时,温度,05,C5,C6,C7,...  ← 画图直接读这个
│     └─ raw/
│        └─ 20261112T114602.json     # 每次采集的完整原始 JSON，永不修改
└─ settings.json                     # 窗口大小、单位偏好、监控间隔等
```

- `disks.json`：`{serial: {model, capacity, interface, first_seen, last_seen, last_device, label}}`；
- `attributes.csv`：表头随首次出现的指标自动扩展（列只增不减），**Excel 直接能打开**，这是文件存储相对数据库的最大好处；
- `raw/*.json`：设计文档第 307 行强调的"保存完整原始 JSON"必须保留——以后想加指标，重放历史即可，不用重新插盘。

**并发/损坏防护**（文件存储唯一的真实风险）：
写入用"临时文件 + 原子替换"（`os.replace`），CSV 追加用 `open(..., 'a')` 单次 flush，
避免断电时留下半行。这个成本很低，但必须做。

## 九、实测补充（P0 完成后的事实修订）

以下均为在本机用 7.5 win64 实测出来的结果，与第二、三节的推测有出入的地方，以本节为准。

### 9.1 权限的真实影响面（比预想的温和）

| 内容 | 非管理员 | 管理员 |
|---|---|---|
| SMART 属性表（05/C5/C6/温度/通电时间） | ✅ 可读 | ✅ 可读 |
| 设备身份（型号/序列号） | ✅ 可读 | ✅ 可读 |
| **容量、转速、ATA 版本（IDENTIFY 块）** | ❌ 缺失 | ✅ 可读 |
| SMART 错误日志 / 自检日志 | ❌ 拒绝 | ✅ 可读 |
| 触发自检（-t） | ❌ | ✅ |

- 回答"我可以手动给它权限么"：可以。右键 `run_as_admin.bat` → 以管理员身份运行即可；
  普通权限也能用，只是容量显示为"未知"、日志页读不到，程序会在界面明确提示。
- **JSON 输出里不会记录"权限不足"**，这个信息只在文本 stdout 里。程序靠
  "退出码 bit2 + 属性在但日志缺"来推断，并据此提示。

### 9.2 Windows 设备名的实测坑

`--scan-open` 返回 `/dev/sda`，但在本机 `smartctl -d ata /dev/sda` 会报
`open device: /Device/Harddisk0/Partition0 failed: Invalid argument`——
`/dev/sdX` 在 Windows 上会被解析到分区而不是整盘，**不稳定**。

结论：程序统一用 `/dev/pdN`（直映 `\\.\PhysicalDriveN`）探测，`--scan-open` 只做兜底。
`pdN` 序号与 WMI `Win32_DiskDrive.Index` 一一对应，非管理员拿不到容量时用它补齐。

### 9.3 其他修订

- `-j -x` 与 `-j -a` 体积几乎一样（9.4KB vs 9.2KB），采集用 `-x`，多点信息不亏。
- 首次快照没有基线，除"本应为 0"的指标（C5/C6/介质错误）外，累计型计数
  （重映射、坏块、ECC）非零只记为"提示"不报警——避免像 870 EVO 的
  `Added_Bad_Flash_Blk_Ct=788` 这种历史遗留值一上来就吓人。
- 数据目录按**序列号**建文件夹已实现（`data/snapshots/<序列号>/`），
  并处理了两个边界：序列号里的非法字符会清洗；同一序列号但容量从 0 变成真实值
  （提权后信息补全）不会被误判成另一块盘。
